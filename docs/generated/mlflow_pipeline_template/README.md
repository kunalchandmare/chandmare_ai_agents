# mlflow_pipeline_template — Documentation

## Overview

`mlflow-pipeline-template` is a pip-installable CLI tool that generates a fully structured MLflow + Hydra pipeline project from two user-provided YAML files.

---

## Installation

```bash
pip install chandmare-mlflow-pipeline-template
```

---

## Command

```bash
# Generate a project (config.yaml and pipeline.yaml in current directory)
mlflow-pipeline-template generate ./my_project

# Specify custom config file paths
mlflow-pipeline-template generate ./my_project --config my_config.yaml --pipeline my_pipeline.yaml
```

---

## Input Files

The user provides exactly **two YAML files**:

### 1. `config.yaml` — Project-level configuration

```yaml
project_name: "my_ml_project"
tracking_backend: "mlflow"       # mlflow | wandb
artifact_backend: "dvc"          # dvc only
mlflow_version: "2.14.1"
# wandb_entity: "myteam"        # only if tracking_backend: wandb (MLflow orchestration still applies)
# wandb_project: "my_project"   # only if tracking_backend: wandb (MLflow orchestration still applies)
dvc_remote: "path/storage"     # example for artifact_backend: dvc
```

| Parameter | Type | Default | Description |
|---|---|---|---|
| `project_name` | str | *(required)* | Project name, used as MLflow project name and folder name |
| `tracking_backend` | str | `"mlflow"` | Experiment tracking backend: `mlflow` or `wandb` |
| `artifact_backend` | str | `"dvc"` | Artifact versioning backend: `dvc` only |
| `mlflow_version` | str | `"2.14.1"` | MLflow version to pin in generated environments |
| `wandb_entity` | str | `""` | W&B entity (only when `tracking_backend: wandb`) |
| `wandb_project` | str | `project_name` | W&B project name (only when `tracking_backend: wandb`) |
| `wandb_version` | str | `"0.17.0"` | W&B version (only when `tracking_backend: wandb`) |
| `dvc_remote` | str | `""` | DVC remote URL (only when `artifact_backend: dvc`) |

Even when `tracking_backend` is `wandb`, the generated project still uses MLflow for orchestration in `main.py`.

### 2. `pipeline.yaml` — Pipeline definition

```yaml
steps:
  clean:
    description: "Apply data cleaning"
    arguments:
      input_artifact:
        type: str
        required: true
        description: "Input artifact"
      min_price:
        type: float
        default: 10.0
        description: "Minimum price threshold"

components:
  download_data:
    description: "Generic artifact downloader"
    arguments:
      artifact_name:
        type: str
        required: true
        description: "Artifact to download"
```

#### Argument schema

Each argument under `arguments:` supports:

| Field | Type | Required | Description |
|---|---|---|---|
| `type` | str | yes | Python type: `str`, `int`, `float`, `bool` |
| `default` | any | no | Default value. If absent, argument is required |
| `required` | bool | no | Explicitly mark as required (default: `false`) |
| `description` | str | yes | Help text for argparse and MLproject |

Arguments auto-propagate to:
- `run.py` → `argparse.add_argument()` calls
- `MLproject` → `parameters:` section

## Architecture: components/ vs src/

### `src/` — Project-Specific Steps

Steps defined under `steps:` in `pipeline.yaml`. They contain **domain logic** — know column names, thresholds, model architecture.

- ❌ Not reusable across projects
- ✅ Contains the actual ML intelligence
- Examples: `clean`, `train`, `feature_eng`, `evaluate`

### `components/` — Reusable, Schema-Agnostic Blocks

Components defined under `components:` in `pipeline.yaml`. They are **generic** — work with any data without modification.

- ✅ Reusable across any project
- ❌ Must NOT contain domain logic
- Examples: `download_data`, `train_val_test_split`, `test_model`

### Decision flowchart

```
Does the step know column names, data types, or business rules?
  YES → put it under steps: (generates to src/)
  NO  → Does it operate on artifacts as opaque files?
    YES → put it under components: (generates to components/)
    NO  → probably doesn't belong in the pipeline
```

## Generated Project Structure

```text
<project_name>/
├── main.py                          ← Hydra orchestrator
├── MLproject                        ← root MLflow entry point
├── config.yaml                      ← runtime values for step arguments
├── pipeline.yaml                    ← copied from input (structural reference)
├── conda.yml                        ← generated by create_env_agent
│
├── components/
│   └── <component_name>/
│       ├── run.py
│       ├── MLproject
│       └── conda.yml                ← generated by create_env_agent
│
└── src/
    └── <step_name>/
        ├── run.py
        ├── MLproject
        └── conda.yml                ← generated by create_env_agent
```

## Backend Roles

### MLflow

Used for orchestration and experiment logging in the generated project.

### DVC

Git-like data versioning for large datasets. Uses `dvc add`, `dvc push`, `dvc pull`.

### W&B

Tracking backend only. Enable it with `tracking_backend: wandb`; it works alongside the MLflow-based orchestrator and is not an artifact backend.

## Repository layout

```text
packages/mlflow_pipeline_template/
├── pyproject.toml              ← package metadata, entry point, dependencies
├── README.md                   ← package README (brief)
├── config.yaml.sample          ← example config.yaml for users to copy
├── pipeline.yaml.sample        ← example pipeline.yaml for users to copy
└── src/mlflow_pipeline_template/
    ├── __init__.py             ← package version
    ├── cli.py                  ← CLI entry point (argparse, dispatches to generator)
    ├── generator.py            ← core logic: reads YAML, renders templates, writes output
    └── template/               ← Jinja templates shipped with the package
        ├── AGENTS.md.jinja
        ├── main.py.jinja
        ├── MLproject.jinja
        ├── config.yaml.jinja
        ├── components/shared/
        │   └── artifact_utils/
        └── _blueprints/
            ├── step/           ← run.py.jinja, run_dvc.py.jinja, run_wandb.py.jinja, MLproject.jinja
            └── component/      ← same variants
```

### Key files

| File | Purpose |
|---|---|
| `cli.py` | Parses `mlflow-pipeline-template generate` command, validates inputs, calls `generator.py` |
| `generator.py` | Reads config.yaml + pipeline.yaml, renders templates, writes output project |
| `_blueprints/step/run.py.jinja` | Template for `src/<step>/run.py` — argparse from pipeline.yaml arguments |
| `_blueprints/step/MLproject.jinja` | Template for `src/<step>/MLproject` — parameters from pipeline.yaml |
| `components/shared/artifact_utils/` | Utility files included in generated project |

## Adding steps to an existing project

1. Edit `pipeline.yaml` — add new step/component definition
2. Re-run: `mlflow-pipeline-template generate . --config config.yaml --pipeline pipeline.yaml`
3. Existing `run.py` files are **never overwritten** — only new folders are created
4. Run `create_env_agent` to regenerate `conda.yml` for new steps
